## Canonical rule

`frontendpages` is the integration target. Source repositories are capability sources, not replacements. A source screen is migrated only when it is materially unique or materially stronger than the canonical implementation. Existing canonical pages are never overwritten merely because another repository contains a similarly named screen.

### Current scoring rule

**Do not migrate a screen solely because it exists.** Each candidate receives:

- **+25** unique capability not represented canonically
- **+20** materially better interaction model
- **+15** stronger accessibility/responsive behavior
- **+15** stronger component reuse
- **+10** stronger data-contract alignment
- **+10** meaningful domain value to a commercial pillar
- **+5** testability/documentation evidence
- **−40** hard-coded mock backend behavior
- **−30** `@ts-nocheck` or equivalent type suppression
- **−30** placeholder/autogenerated-only implementation
- **−25** fake mutation/query plumbing

A candidate must clear the quality gate before code migration. A visually useful but mocked screen may be retained as a design reference without being represented as a live capability.

## Important findings from the first comparison

`ShadowChat-Core`'s `TransactionHistory` and `ProductSearchScreen` are **not currently safe direct migrations**. Their inspected implementations contain `@ts-nocheck`, autogenerated-draft markers, fake tRPC proxies, local stub hooks, simulated delays, and hard-coded/mock data. They therefore belong in the **design-harvest / rebuild queue**, not the production-capability queue.

This is intentional: preserving unique product concepts does not mean importing false production evidence.

## Release discipline

No migrated frontend screen may claim live wallets, balances, prices, transactions, payments, vendor integrations, AI responses, blockchain state, monitoring, or other external success unless its contract and acceptance evidence are verified. Design-only functionality must remain explicitly bounded.

# Three-Frontend Unified Integration

## Canonical target

`frontendpages` is the canonical frontend integration target.

## Source repositories

| Repository | Role | Integration rule |
| --- | --- | --- |
| `frontendpages` | Canonical foundation | Preserve its strongest shell, routing, shared components, and verified pages. |
| `ShadowChat-Pro-Edition` | Frontend-rich source | Harvest unique pages and stronger implementations after comparison. |
| `ShadowChat-Core` | Unique capability source | Preserve distinctive screens and concepts; harden generated/draft implementations before promotion. |

## Verified gap candidates

The current comparison identified frontend capability candidates that are not present by the same implementation names in `frontendpages` and are represented by source work in the ShadowChat family:

- Crypto/community feed
- Jurisdiction selection and regional policy boundary
- Live rankings/reputation
- Product search/discovery
- Financial reports
- Transaction history
- Cross-repository migration/provenance tracking

## Next integration sequence

1. Wire the new screens into the canonical route registry.
2. Compare `ShadowChat-Pro-Edition` page implementations against same-domain canonical pages.
3. Harvest only unique or demonstrably stronger implementations.
4. Add migration provenance for every harvested screen.
5. Run TypeScript/build/tests and fix integration regressions.
6. Add CI/security checks for the merged frontend.
7. Repeat the gap scan until the three-repository delta is exhausted.

## Completion rule

A frontend capability is considered integrated only when its implementation exists in the canonical repository, its route is reachable, its dependencies resolve, its data requirements are documented, and the relevant validation checks pass.
